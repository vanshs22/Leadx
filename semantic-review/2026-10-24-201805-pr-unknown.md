# Local durable validation and readiness hardening

This change adds a provider-isolated SQLite data plane for local validation, wires it through the Supabase client boundary, hardens Docker/Compose health checks, extends the migration chain, and aggregates database, cache, auth, worker, queue, and reclaim readiness. The overall production boundary is deliberately fail-closed: local mode denies remote providers and hardened environments reject local authentication. **Watch for:** **confirmed** local composite upserts can overwrite unrelated rows; **confirmed** the root full-migration mirror omits durable recovery indexes and mission-attempt writes; **confirmed** the local gate’s synthetic lifecycle uses `FakeSupabase`, so its PASS evidence does not exercise the SQLite adapter. Remote evidence is correctly marked unverified.

**Verdict**: NEEDS_CHANGES

## High-level view

The local data path is selected only when both local validation and the SQLite backend are enabled, while other Supabase access is denied by the provider-isolation boundary. Its generic upsert implementation is unsafe for the composite keys used by application code.

The migration directory has 35 ordered files, but the clean-install mirror is not behaviorally equivalent to that chain: durable recovery definitions are emitted in a later appended block, and several indexes plus mission-task attempt persistence are absent. This creates divergent fresh-install behavior depending on which documented install path is used.

Readiness aggregation now requires fresh worker heartbeat, queue, and reclaim evidence, and Compose checks container health. The checked-in report explicitly separates local PASS records from remote UNVERIFIED records, but the local synthetic PASS is based on fakes rather than the SQLite adapter and should not be read as proof of the durable local data path.

### Composite conflict handling in the local durable adapter

**confirmed** `sqlfix_latest/app/memory/local_durable.py:300-310` compares `current_row.get(self.conflict_column)` with `row.get(self.conflict_column)` without splitting comma-separated Supabase conflict specifications. For `on_conflict="tenant_id,lead_id"`, both lookups return `None`, so every subsequent upsert matches the first row regardless of tenant or lead. A direct two-write reproduction leaves only the second payload in the table. This can corrupt any local validation flow using composite keys such as `tenant_id,lead_id`, `tenant_id,provider`, or `run_id,lead_id`.

### Canonical migration versus the root mirror

**confirmed** `sqlfix_latest/supabase/migrations/20261001000950_leadx_16_durable_task_recovery.sql:11-17,37-40,58,80,100-101` creates `idx_jobs_retry_after`, `idx_job_operations_principal`, `idx_mission_tasks_owner`, the attempt/quota indexes, and `idx_worker_heartbeats_capability`; none of those index definitions occurs in `sqlfix_latest/SUPABASE_FULL_MIGRATION.sql:11128-11199`. The mirror also defines `leadx_claim_mission_task` at `SUPABASE_FULL_MIGRATION.sql:11207-11209` as a direct update, while the canonical function at `.../20261001000950_leadx_16_durable_task_recovery.sql:162-179` inserts an `agent_mission_task_attempts` row, and the canonical reaper updates that attempt at lines 195-212. A fresh install from the mirror therefore loses durable mission-attempt history and its associated query support even though the migration policy calls the file a clean-install mirror.

The mirror’s `CANONICAL MIGRATION 26` marker is immediately followed by migration 27, while the durable block is appended after the realtime section at `SUPABASE_FULL_MIGRATION.sql:11128-11219`; this is a **likely** ordering/maintenance hazard even where deferred PostgreSQL function parsing allows the final script to run. `sqlfix_latest/MIGRATION_POLICY.md:5-12` also says the chain ends with five LeadX 16 data-plane migrations but lists six files, a **confirmed** documentation mismatch that makes lineage review less reliable.

### Scope and truthfulness of local validation evidence

**confirmed** `sqlfix_latest/scripts/synthetic_validation.py` imports `FakeSupabase` from `tests.conftest` and uses it for quota settlement; its CRM state and authoritative refetch are ordinary Python dictionaries. The checked-in `sqlfix_latest/artifacts/local-validation/evidence.json:48-143` reports all local records as PASS, while remote records are correctly `UNVERIFIED`. That remote separation is truthful, but the local PASS does not establish that the SQLite adapter preserves composite records or that the actual shared Compose volume survives restart. Add an adapter-backed integration record to the gate, or constrain the report wording to static/fake-fixture validation.

The readiness aggregation in `sqlfix_latest/app/app_service.py:565-600` requires queue capability, a fresh heartbeat, and reclaim evidence from a healthy worker, and `:633-674` includes those required components in the final boolean. The remaining production validation boundary is explicit: `evidence.json` marks Supabase, external providers, billing, delivery, and deployment as unverified rather than claiming them.
