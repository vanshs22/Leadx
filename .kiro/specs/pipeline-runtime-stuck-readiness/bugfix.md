# Bugfix Requirements Document

## Introduction

LeadX pipeline validation cannot currently establish whether an authorized lead-generation run is fast, progressing, safely stoppable, and complete. In the reported case, the pipeline runs too slowly, can remain in a partial or stuck state, and can fail to assign or deliver leads even after upstream processing appears to progress. This bugfix defines a bounded readiness and runtime-correction scope using the local Docker Compose project while exercising its configured real Supabase and provider paths, with only already-provisioned controlled test data. It does not authorize disabling authentication, tenant isolation, row-level security, policies, quotas, or other production protections, and it does not authorize secret disclosure or unbounded external-provider activity.

For this document, `C(X)` is a run or validation state with missing measurable progress, an indefinite or unexplained partial/stuck outcome, a stop-condition violation, an assignment or delivery count mismatch, or readiness evidence that cannot distinguish a real runtime result from a blocked or synthetic test. `F` is the current behavior and `F'` is the corrected behavior. Fix checking covers every input satisfying `C(X)`; preservation checking covers every input not satisfying `C(X)`.

The previously unavailable readiness evidence must be rechecked through the local Docker Compose project's real configured authentication, Supabase, provider, API, worker, queue, delivery, and performance paths in an explicitly identified authorized environment. Synthetic unit fixtures may continue to prove contracts in tests, but local synthetic runtime authentication or provider behavior must not be used as readiness evidence. Any contract substitute must be labeled as such and must not be represented as proof of the configured Supabase/provider project, a live provider, or a production outcome.

This clarification limits the transition to a non-secret identity and configuration-capability check for the local Docker Compose project, a bounded authenticated run through its configured real Supabase/provider paths, role and tenant verification, protected-route and session checks, pipeline assignment and delivery reconciliation, and a dependency-gated performance measurement. It records exact outcomes for each scope and records unavailable credentials, accounts, provider budgets, email sandbox or recipient approval, cleanup, or real provider/SES/CRM/realtime/production scopes as `BLOCKED` or `NOT TESTED`. It does not use shared or production services, contact real recipients, access or print `.env` secrets, call live providers without an approved bounded budget, or run production actions unless the environment identity, authorized existing test accounts, tenant scope, provider permissions, and bounded recipient or side effect are explicitly identified and approved.

This document also includes a focused admin/client authentication follow-up for the authorized environment. The reported symptom is that submitting credentials at `http://localhost:3000/admin/login` displays `Request could not be completed`; the same request contract and protected behavior must be verified through the real configured portal/API path used by the project, not only through local synthetic authentication. Diagnosis and correction are limited to redacted API and portal evidence, configured auth/provider paths, real bounded admin and client test identities, tenant membership, CORS and cookie/session behavior, protected routes, pipeline delivery, performance, and health/readiness dependencies. Local synthetic-mode behavior may be disabled or bypassed only in the runtime path under test and must not be used to obtain a readiness pass. The follow-up must not disable authentication, authorization, RLS, tenant isolation, policies, quotas, rate limits, provider guards, outbound protections, audit controls, or stop controls; must not reset users or modify production/shared data; and must not expose `.env` values, secrets, tokens, or passwords.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN an authorized controlled pipeline run is submitted, especially for a small target such as five leads, THEN the system can take substantially longer than the expected bounded test window or remain in `running` without a current progress signal, lease explanation, terminal reason, or actionable blocker.

1.2 WHEN a worker, queue item, provider call, or lease stops making progress during a run THEN the system can leave the run or related work in `running` or `partial` without converging to a truthful terminal or recoverable state.

1.3 WHEN a run reaches its target, is cancelled, times out, or loses ownership THEN in-flight or queued work can continue, late results can write after the stop decision, or provider work can continue beyond the required target and budget.

1.4 WHEN leads pass enrichment, verification, scoring, or the quality gate THEN assignment or delivery can remain incomplete, and discovered, qualified, assigned, reserved, and delivered counts can disagree without an actionable reconciliation result.

1.5 WHEN runtime speed and readiness are assessed THEN evidence can omit stage timing, queue/provider activity, stop reason, authoritative counts, or the distinction between live, local, synthetic, blocked, and untested behavior, preventing a reliable diagnosis of the delay.

1.6 WHEN someone attempts to make testing pass by disabling authentication, tenant isolation, row-level security, policies, or other blockages THEN the resulting evidence can be unsafe or invalid because it does not prove the protected production path and can expose data or permit cross-tenant effects.

1.7 WHEN readiness depends on remote Supabase schema/RLS behavior, deployed API/worker/queue health, real provider yield or latency, external quotas or rate limits, deliverability, live CRM/client projection, deployed realtime, or a production 20–30 second target THEN the existing plan can record the item as `BLOCKED` or `NOT TESTED` without specifying a safe substitute, the evidence boundary, or the condition for a later controlled check.

1.8 WHEN readiness validation begins without the local Docker Compose project identity, configured real Supabase/provider capability, existing authorized admin/client test accounts, tenant scope, or safe side-effect and cleanup boundaries THEN the required API/worker/queue, authentication, provider, delivery, and performance checks remain blocked or untested, and the run has no verified execution boundary.

1.9 WHEN a previously `BLOCKED` or `NOT TESTED` check is rerun without a non-secret local Compose environment/configuration preflight, existing authorized admin/client test accounts, tenant-membership check, protected authenticated path, provider budget, rollback or cleanup plan, or explicit outcome record THEN the resulting evidence can be incomplete, unsafe, or falsely treated as readiness proof.

1.10 WHEN the local Docker Compose project identity or configured real authentication, Supabase, provider, SES, CRM, realtime, or production capability cannot be verified safely THEN local synthetic runtime behavior can be mistaken for proof of that scope, or the real scope can be omitted instead of being recorded as `BLOCKED` or `NOT TESTED`.

1.11 WHEN an authorized admin or client submits credentials through the real configured portal/API path, including the reported `http://localhost:3000/admin/login` path when that is the named project environment THEN the portal can display `Request could not be completed` instead of exposing a truthful success, invalid-credential, unavailable-dependency, or configuration error outcome.

1.12 WHEN the configured admin or client login fails THEN the available portal, browser, and API evidence can be insufficient to determine whether the request URL, method, payload, response contract, auth/provider configuration, CORS policy, cookie attributes, session handling, tenant membership, or API/portal health dependency caused the failure.

1.13 WHEN authentication validation needs an admin or client identity THEN the test can lack an already-provisioned authorized account with verified role and tenant membership, or can risk using a real password, shared user, production account, or shared tenant data.

1.14 WHEN configured admin or client login is exercised after an API, portal, worker, queue, auth, provider, or readiness dependency is unavailable THEN the UI can collapse the dependency failure into the same generic `Request could not be completed` message without identifying the blocked readiness boundary.

1.15 WHEN configured login behavior is corrected only for the visible success case THEN invalid credentials, role and tenant authorization, session persistence and expiry, logout, protected-route enforcement, pipeline delivery, or performance can regress or remain unverified.

1.16 WHEN a login diagnosis or regression run records evidence THEN logs or artifacts can contain credentials, tokens, cookies, raw authorization headers, `.env` values, passwords, tenant-sensitive payloads, or other secrets.

1.17 WHEN readiness validation uses local synthetic authentication or provider behavior in the runtime path instead of the real configured project paths THEN evidence can pass without exercising the actual authentication, provider guards, tenant membership, session, delivery, or performance behavior.

1.18 WHEN the environment, authorized roles, tenant memberships, bounded recipient or provider permission, and rollback plan are not identified before a real-path check THEN the check can contact an unintended service, affect an unintended tenant or recipient, or leave no safe way to restore test state.

1.19 WHEN real admin and client roles, tenant membership, session lifecycle, protected routes, pipeline assignment and delivery, and configured-path performance are not exercised THEN readiness can be reported despite failure in the production-shaped project path.

1.20 WHEN the local Docker Compose stack is connected to a configured Supabase project without a non-secret check of the intended environment and project identity, configured URL/key capability, existing authorized admin and client test accounts, tenant memberships, RLS/tenant isolation, migration/schema compatibility, provider and email budgets, approved recipient or sandbox, rollback, cleanup, and production-data boundaries THEN the live-readiness check can run against an unconfirmed target or without a safe recovery boundary.

1.21 WHEN a bounded live-readiness check begins without confirming that the local stack, Supabase project, authenticated roles, schema, provider permissions, outbound budget, recipient boundary, and cleanup owner all refer to the same authorized test scope THEN the check can mix local, shared, or production state and produce evidence that cannot be trusted.

1.22 WHEN the live check has no dependency order or explicit stop conditions THEN it can continue after an identity mismatch, failed auth/RLS/tenant check, schema incompatibility, unhealthy service, missing budget, quota or rate-limit response, target completion, timeout, unsafe side effect, count mismatch, or cleanup failure.

1.23 WHEN Supabase login capability is validated by reading or printing secret values, exposing tokens, or asking the user to paste credentials THEN the validation can disclose secrets and still fail to prove that the protected application path is safe.

### Expected Behavior (Correct)

2.1 WHEN an authorized controlled pipeline run starts THEN the system SHALL record a start time, target, run identity, tenant scope, stage transitions, heartbeat or lease state, and bounded progress updates, and SHALL reach a truthful terminal or recoverable status within the configured test window rather than remain indefinitely `running`.

2.2 WHEN a worker, queue item, provider call, or lease stops making progress THEN the system SHALL detect the bounded timeout or stale ownership, stop new work, fence unsafe late writes, classify the cause, reconcile related work, and expose an actionable terminal or recoverable outcome without deleting valid lead data.

2.3 WHEN the target is met, or a run is cancelled, timed out, or loses ownership THEN the system SHALL stop admitting new work, cancel safe in-flight work, prevent post-stop provider activity where supported, reject stale writes, and persist one idempotent stop reason with the final authoritative counts.

2.4 WHEN a lead satisfies the applicable qualification and contact requirements THEN the system SHALL perform tenant-authorized assignment and delivery through idempotent state transitions, reconcile discovered, qualified, assigned, reserved, and delivered counts before reporting completion, and expose any shortfall or blocked delivery reason instead of silently leaving `partial`.

2.5 WHEN speed or readiness is measured THEN the system SHALL produce a bounded evidence record containing the environment and evidence class, target, total and per-stage elapsed time, queue and provider outcomes, timeout/cancellation outcomes, stop reason, failures, and authoritative assigned, reserved, and delivered counts. The system SHALL report an unsupported latency target as unverified rather than claim that the run completes in seconds without matching evidence.

2.6 WHEN runtime validation is performed THEN the system SHALL use the local Docker Compose project as the named runtime environment and SHALL exercise its configured real authentication, Supabase, provider, API, worker, queue, assignment, delivery, and session paths with already-provisioned authorized admin and client test accounts and verified tenant membership. Local synthetic runtime authentication or provider behavior SHALL not produce readiness evidence. Authentication, tenant isolation, row-level security, policies, quotas, rate limits, provider guards, outbound protections, audit controls, and stop controls SHALL remain enabled. Outbound email, outreach, campaigns, billing, and unapproved provider side effects SHALL remain disabled or explicitly bounded, and missing credentials, accounts, configuration capability, provider budgets, or dependencies SHALL be reported as `BLOCKED` or `NOT TESTED`.

2.7 WHEN a run cannot complete because of an unavailable dependency, provider, credential, schema, queue, or configuration prerequisite THEN the system SHALL identify that blocker in the run and readiness evidence, stop safely, and avoid presenting the result as a runtime speed or delivery success.

2.8 WHEN Supabase schema, RLS, authentication, or tenant-isolation behavior is unavailable in the local Docker Compose project's configured real path THEN validation SHALL use an ephemeral or isolated local/staging database with the applicable migrations, RLS, policies, and disposable fixtures only as a contract fallback. Readiness evidence for the configured real Supabase project SHALL require the configured authentication path, already-provisioned authorized admin and client test accounts, verified tenant memberships, and protected requests in the named environment; a synthetic local principal or synthetic runtime mode SHALL not substitute for that evidence. Read-only schema inspection and protected contract tests SHALL be allowed; production or shared tenant data SHALL not be used. The result SHALL remain `BLOCKED` or `NOT TESTED` for the configured Supabase behavior unless that behavior is exercised in the explicitly controlled authorized path.

2.9 WHEN deployed API, worker, or queue health is unavailable THEN validation SHALL use the local Docker Compose project's documented configured project path with the real Supabase/provider configuration and already-provisioned authorized admin and client requests, verified tenant membership, bounded test jobs, and read-only health/lease/recovery checks. A queue or service health check SHALL not bypass authorization or use synthetic runtime authentication. A local profile with synthetic authentication MAY prove only an isolated contract and SHALL not be used as readiness evidence for the configured project. The result SHALL remain `BLOCKED` or `NOT TESTED` for any configured deployed behavior that was not exercised.

2.10 WHEN real provider yield or latency is authorized for the local Docker Compose project's configured provider path THEN validation SHALL use that real provider path with the smallest bounded budget, explicit provider permission, stop guards, and synthetic or approved test inputs. WHEN that real path is unavailable or unsafe to exercise THEN validation SHALL use deterministic provider contract fixtures, deny-all adapters, and controlled provider fakes to test routing, timeout, cancellation, budgeting, result normalization, and evidence classification. Mock or local timing SHALL be labeled as contract evidence and SHALL remain `BLOCKED` or `NOT TESTED` for real-provider yield or latency. No real provider call SHALL begin without an available approved budget.

2.11 WHEN external provider quotas or rate limits are unavailable for validation THEN validation SHALL use deterministic quota counters, rate-limit fixtures, retry-after responses, and the smallest authorized staging budget to prove that limits are enforced. Quotas and rate limits SHALL remain enabled and SHALL not be raised, disabled, or bypassed to obtain a pass. External-provider quota or rate-limit behavior SHALL remain `NOT TESTED` when no controlled provider account is exercised.

2.12 WHEN deliverability is unavailable or live email is not explicitly authorized THEN validation SHALL use a local mail sink or provider-send contract fixture to prove message formation, recipient/sender policy, handoff, suppression, and failure handling without sending to a real recipient. A separately authorized provider sandbox and isolated test inbox MAY verify acceptance and receipt. No email send SHALL occur without an approved email sandbox or explicitly approved bounded recipient. A local sink SHALL not be reported as inbox deliverability, and real deliverability SHALL remain `NOT TESTED` when no controlled inbox path is exercised.

2.13 WHEN live CRM or client projection is unavailable THEN validation SHALL use tenant-scoped synthetic CRM/client fixtures or an isolated staging CRM sandbox to test authenticated writes, idempotency, read-back, assignment visibility, and shortfall handling. The result SHALL remain `NOT TESTED` for the live CRM/client projection when no live isolated projection is exercised, and fixture data SHALL not be mixed with working client data.

2.14 WHEN deployed realtime behavior is unavailable THEN validation SHALL use a local or isolated staging realtime channel with synthetic authenticated subscribers and tenant-scoped events to verify authorization, event shape, ordering or reconciliation behavior, and disconnect recovery. The result SHALL remain `NOT TESTED` for deployed production realtime when that deployment is not exercised; polling or a static response SHALL not be counted as realtime evidence.

2.15 WHEN the production 20–30 second target is unavailable for direct controlled measurement THEN local unit or synthetic timing SHALL be used only for regression and bounded-stage evidence. A configured-project result SHALL require the local Docker Compose project, its real configured authentication and provider paths where applicable, already-provisioned authorized admin/client accounts and tenant scope, isolated test data, authorized dependencies and provider budget, recorded total and stage timings, and no forbidden side effects. The production target SHALL remain `BLOCKED` or `NOT TESTED` unless those conditions are met; a unit or synthetic pass SHALL not promote it to production readiness.

2.16 WHEN credentials, existing test accounts, schema, queue, provider budget, deployment, or configuration prerequisites are missing THEN validation SHALL run a non-secret preflight that checks only environment identity, presence, reachability, and safe configuration capability where permitted, and SHALL also exercise an unavailable-dependency fixture to verify classification. Secrets, tokens, raw payloads, and `.env` values SHALL never appear in logs or evidence. An unavailable prerequisite SHALL produce `BLOCKED` when the required check was attempted and could not run, or `NOT TESTED` when the check was intentionally not exercised or lacks an authorized environment.

2.17 WHEN any validation result is recorded THEN the evidence SHALL include the exact check name, timestamp, environment and evidence class, target and metric, authenticated test scope, dependency/provider mode, total and stage timings where applicable, queue/lease/timeout/cancellation outcomes, stop reason, authoritative counts, forbidden-action counters, sanitized failure or blocker category, and a reference to the artifact proving the result. Evidence SHALL contain no secrets, raw provider credentials, tenant-sensitive payloads, or unbounded production data.

2.18 WHEN a check executes all applicable assertions in its declared environment and the assertions pass with the required evidence THEN the result SHALL be `PASS` and SHALL state the evidence class. `PASS` SHALL apply only to the exercised scope and SHALL not imply that unexercised deployed, provider, deliverability, CRM, realtime, or production behavior also passed.

2.19 WHEN a check executes and an applicable assertion fails, a protection is violated, a count cannot reconcile, a stop fence is bypassed, or an unsafe side effect occurs THEN the result SHALL be `FAIL`, the readiness gate SHALL remain closed for the affected scope, and the evidence SHALL record the sanitized failure and affected tenant/run scope.

2.20 WHEN a required check is attempted but a dependency or authorized environment is unavailable THEN the result SHALL be `BLOCKED` with the dependency, attempted validation path, sanitized reason, and safe next step. `BLOCKED` SHALL never be converted to `PASS` by disabling authentication, RLS, tenant isolation, quotas, rate limits, provider guards, or production protections.

2.21 WHEN a check is not executed because it lacks authorization, a controlled environment, an approved test principal, or a required evidence path THEN the result SHALL be `NOT TESTED` with the missing prerequisite and the safe validation path that would be required later. `NOT TESTED` SHALL not be treated as a pass, latency proof, delivery proof, or production-readiness decision.

2.22 WHEN full-coverage readiness is evaluated THEN the system SHALL use the local Docker Compose project with its configured real authentication and provider paths, already-provisioned authorized admin and client test identities, verified tenant memberships, and service-role access limited to approved test fixture setup and teardown. The validation SHALL use synthetic unit fixtures only for unit/contract scopes that cannot safely use the configured path, deterministic provider mocks or an authorized provider sandbox only for scopes that cannot safely use the real provider, quota and rate-limit simulations, a mail sink or explicitly approved bounded recipient, CRM and realtime test doubles where necessary, and read-only production health checks according to the dependency under test; production data and unapproved production side effects SHALL not be used. Contract, authorization, lifecycle, fencing, reconciliation, classification, and protection tests MAY produce `PASS` only for their declared scope, while real provider yield or latency, external quota or rate-limit enforcement, email acceptance or receipt, live CRM projection, deployed realtime, and production latency SHALL require the corresponding configured path, authorized sandbox, or isolated deployment and otherwise remain `BLOCKED` or `NOT TESTED`.

2.23 WHEN the follow-up execution starts THEN the system SHALL perform a non-secret environment and capability preflight that identifies the local Docker Compose project and its configured real Supabase/provider paths, existing authorized admin and client test accounts, tenant memberships, provider permissions and available budget, allowed side effects and recipient boundary, rollback plan, and cleanup owner without reading or printing `.env` values. The check SHALL verify only safe identity, reachability, and configuration capability, SHALL use only already-provisioned synthetic tenant/test data where permitted, and SHALL produce `BLOCKED` or `NOT TESTED` before any runtime action if the environment, credentials, accounts, permissions, provider budget, required services, rollback, or safe cleanup cannot be established. Docker Compose SHALL be the runtime project under test; local synthetic authentication or provider mode SHALL not replace the configured real paths.

2.24 WHEN the named local Docker Compose environment and its protected prerequisites pass THEN the system SHALL run one bounded authenticated admin/client API, worker, and queue path through the configured real Supabase/provider project paths, including queue reachability, claim/renew/complete or recover, heartbeat/progress, terminal or recovery status, tenant authorization, and stop behavior. Authentication, RLS, tenant isolation, quotas, rate limits, provider guards, outbound protections, audit controls, and stop fences SHALL remain enabled. A local synthetic authentication or provider path MAY prove only an isolated unit/contract; it SHALL not be used as readiness evidence for the configured project.

2.25 WHEN the configured project path is eligible for mail validation THEN the system SHALL run the provider-send contract or authorized email sandbox path with an explicitly bounded synthetic or approved test recipient only. The check SHALL verify sender/domain policy, message handoff, suppression and failure handling, and no-send guards without contacting an unapproved real recipient. No provider send SHALL occur unless an approved email sandbox or explicitly approved bounded recipient is available. A mail sink or contract fixture SHALL prove only handoff behavior; real SES acceptance, inbox receipt, and deliverability SHALL remain `BLOCKED` or `NOT TESTED` when no authorized sandbox or explicitly bounded recipient exists, and an unavailable sink or sandbox SHALL produce `BLOCKED`.

2.26 WHEN the named local Docker Compose environment, configured real authentication/provider path, protected API/worker/queue path, existing authorized admin/client accounts, available provider budget, and required benchmark dependencies are eligible THEN the system SHALL rerun the controlled latency benchmark for the bounded target-5 case, or the existing benchmark's smallest declared bounded target, with the configured deadline and stop guards. The benchmark SHALL capture total and stage timings, queue/provider/outbound counters, authoritative discovered/qualified/assigned/reserved/CRM-visible/delivered counts, tenant scope, terminal or stop reason, rollback and cleanup status, and forbidden-action counters. An unresolved dependency, missing authorization, unavailable provider budget, or protection failure SHALL prevent a latency claim and produce `BLOCKED` or `FAIL` as applicable; local unit or synthetic timing SHALL not claim the production 20–30 second target.

2.27 WHEN any follow-up check is executed THEN the system SHALL record exactly one `PASS`, `FAIL`, `BLOCKED`, or `NOT TESTED` outcome with the check name, timestamp, named environment and evidence class, bounded target or metric, authenticated role and tenant scope, dependency/provider mode, sanitized blocker or failure, relevant timings and counters, rollback and cleanup status, and artifact reference. The system SHALL drain or cancel bounded test jobs, purge sink messages where supported, unsubscribe test channels, remove only synthetic rows or fixtures, verify no test work remains, and stop dependent checks if cleanup or restoration is unavailable. Evidence SHALL contain no secrets, tokens, `.env` values, real recipient data, raw provider payloads, shared tenant data, or production data.

2.28 WHEN no explicitly authorized capability exists for a real scope after the follow-up checks THEN the system SHALL explicitly record each unexercised scope as `BLOCKED` or `NOT TESTED`, including configured real Supabase/API/worker/queue behavior, real provider yield or latency, external provider quota or rate-limit behavior, SES acceptance or inbox deliverability, live CRM/client projection, deployed realtime, and production latency. A local Compose contract fixture, mail-sink, or synthetic benchmark `PASS` SHALL not be promoted to any of those scopes.

2.29 WHEN an authorized admin or client submits valid credentials through the real configured portal/API path in the named environment THEN the portal SHALL send the documented request contract to the intended configured API, SHALL establish the authenticated session through the existing secure mechanism, SHALL verify the identity's role and tenant membership, and SHALL expose a successful authenticated result without disabling authentication, authorization, RLS, tenant isolation, or policies.

2.30 WHEN an authorized admin or client submits invalid or unauthorized credentials through the configured login path THEN the portal SHALL remain unauthenticated, SHALL show a safe actionable authentication failure, SHALL not disclose whether protected data exists, and SHALL not present the failure as a generic dependency outage when the API returned an authentication or authorization response.

2.31 WHEN the configured login is diagnosed or corrected THEN the validation SHALL inspect only isolated and redacted portal/API evidence for the browser request, API route and response contract, configured auth/provider capability, CORS result, cookie/session attributes and persistence, role and tenant membership, and API/portal health/readiness dependencies. Evidence SHALL classify the first failing boundary and SHALL not include secrets, passwords, tokens, cookies, raw authorization headers, `.env` values, or shared/production data.

2.32 WHEN configured login requires an authenticated test principal THEN validation SHALL use an already-provisioned, explicitly approved bounded admin identity and client identity with verified tenant membership, supplied through the approved environment mechanism. The identities SHALL be isolated from working client data and SHALL have an existing expiry or cleanup path; validation SHALL not create, reset, or replace users or modify production/shared data.

2.33 WHEN the configured API, portal, auth/provider service, CORS policy, cookie/session path, or health/readiness dependency is unavailable or misconfigured THEN the login check SHALL report the specific sanitized blocker and safe next step, SHALL preserve the existing security controls, and SHALL not convert the result to `PASS` by bypassing authentication or authorization.

2.34 WHEN a valid configured admin or client login succeeds and the browser is refreshed or a new protected request is made within the supported session lifetime THEN the session SHALL persist through the documented secure mechanism, the protected route and tenant-scoped data SHALL remain accessible only to the authenticated authorized principal, and unauthenticated or cross-tenant access SHALL continue to be rejected or redirected.

2.35 WHEN the configured admin/client authentication follow-up is executed THEN regression coverage SHALL exercise successful admin login, successful client login, invalid or unauthorized login, session persistence and expiry, logout, protected-route enforcement, tenant isolation, bounded pipeline assignment and delivery, and the configured-path performance check, and SHALL record one of `PASS`, `FAIL`, `BLOCKED`, or `NOT TESTED` for each case with redacted evidence and no claim beyond the named environment and scope.

2.36 WHEN the local Docker Compose project is selected for readiness validation THEN the runtime path under test SHALL use the configured real authentication and provider selection, SHALL fail closed if those paths or their credentials are unavailable, and SHALL preserve RLS, tenant isolation, authorization, quotas, rate limits, provider guards, outbound protections, audit controls, and stop controls. Synthetic unit fixtures SHALL remain available for unit/contract tests, but synthetic runtime authentication or provider mode SHALL not produce a `PASS` for real project readiness.

2.37 WHEN a real-path check is about to begin THEN the system SHALL require a recorded non-secret environment check naming the local Docker Compose project and configured real Supabase/provider paths, the existing authorized admin and client test accounts, verified tenant memberships, provider permissions and available budget, allowed side effects and approved recipient boundary, data scope, rollback or abort steps, cleanup owner, and evidence destination. If any required item is missing or cannot be verified safely without printing secrets, the system SHALL perform no real-path action and SHALL record `BLOCKED` or `NOT TESTED` with the missing prerequisite.

2.38 WHEN real-path readiness is assessed THEN validation SHALL exercise both the authorized admin and client roles, their tenant memberships, session creation, refresh, expiry and logout, protected routes, cross-tenant denial, bounded pipeline execution, assignment and delivery reconciliation, and configured-path total and stage performance. Each result SHALL identify the role, tenant scope, dependency mode, and exact evidence class.

2.39 WHEN a bounded real-path check fails, exceeds its stop or quota boundary, encounters an unsafe side effect, or cannot be rolled back or cleaned up as planned THEN the system SHALL stop dependent checks, prevent further provider or outbound work where supported, preserve audit evidence, and record `FAIL` or `BLOCKED` rather than continue or claim readiness.

2.40 WHEN the local Docker Compose project permits no safe bounded test identity, recipient or email sandbox approval, provider permission or budget, rollback path, or redacted evidence path THEN the system SHALL not send real email, call live providers, modify real data, reset real users, or run production actions, and SHALL record the affected scope as `BLOCKED` or `NOT TESTED`.

2.41 WHEN the same-day bounded live-readiness check is prepared THEN the system SHALL perform a non-secret preflight before connecting or exercising the stack that identifies the local Docker Compose project, confirms the intended authorized Supabase project identity and environment, verifies configured Supabase URL/key capability without reading or printing secret values, confirms existing authorized admin and client test accounts and tenant memberships, checks protected auth/RLS/tenant-isolation capability, checks migration and schema compatibility without applying destructive migrations, records provider permissions and bounded provider/email budgets, confirms an approved recipient or email sandbox, and names the allowed data scope, rollback/abort steps, cleanup owner, and redacted evidence destination. If any prerequisite is missing, mismatched, unconfirmed, or unsafe to verify, the system SHALL perform no live-path action and SHALL record `BLOCKED` or `NOT TESTED`.

2.42 WHEN the preflight passes THEN the system SHALL run the bounded live-readiness sequence in order: connect only the local Docker Compose services to the confirmed authorized Supabase project; verify service health and configured protected connectivity; authenticate the existing admin and client test accounts; verify role, tenant membership, same-tenant access, cross-tenant denial, unauthenticated denial, and session behavior; perform a read-only migration/schema compatibility check; submit at most one bounded synthetic pipeline run through the normal API, worker, queue, assignment, and delivery path; observe progress, lease/stop behavior, authoritative counts, and terminal or recoverable status; exercise provider calls only within the approved budget; exercise email only through the approved sandbox, sink, or explicitly approved recipient; reconcile results; and execute the declared rollback and cleanup. Each step SHALL record one scoped `PASS`, `FAIL`, `BLOCKED`, or `NOT TESTED` result without promoting local or synthetic evidence to an unexercised external or production claim.

2.43 WHEN any live-readiness stop condition occurs, including an environment or Supabase project identity mismatch, unavailable or unconfirmed configured URL/key capability, missing authorized account or tenant scope, auth/RLS/tenant-isolation failure, migration/schema incompatibility, unhealthy API/worker/queue/dependency, missing provider or email budget, unapproved recipient, quota or rate-limit boundary, target completion, deadline or stale-progress timeout, unexpected outbound or data side effect, stop-fence violation, unreconciled count, rollback failure, or cleanup failure THEN the system SHALL stop the current check, prevent dependent checks and further provider/outbound work where supported, preserve sanitized evidence, and record `FAIL` for a violated assertion or protection and `BLOCKED` for an unavailable or unsafe prerequisite. The system SHALL not continue to obtain a passing result.

2.44 WHEN configured Supabase login capability is checked THEN the system SHALL use the existing project configuration through its approved runtime mechanism, inspect only non-secret identity/capability outcomes, redact credentials and tokens, never read or print secret values, and never ask the user to paste them. A missing or unusable configured capability SHALL be recorded as `BLOCKED` or `NOT TESTED`.

2.45 WHEN the bounded live-readiness check executes THEN the system SHALL keep authentication, authorization, RLS, tenant isolation, policies, quotas, rate limits, provider guards, outbound protections, audit controls, and stop controls enabled; SHALL not apply destructive migrations, reset or replace users, use an unconfirmed target, send unapproved email, or modify production/shared data; and SHALL use only disposable approved test data and the declared rollback/cleanup boundary.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN an authorized run is healthy and progressing THEN the system SHALL CONTINUE TO preserve its existing discovery, enrichment, qualification, assignment, delivery, retry, cancellation, and terminal-state behavior.

3.2 WHEN a run is outside the reported stuck, slow, partial, assignment, delivery, or measurement condition THEN the system SHALL CONTINUE TO preserve valid lead records, provenance, tenant/use-case policy, exclusivity decisions, quotas, and existing provider contracts.

3.3 WHEN authentication, tenant isolation, row-level security, authorization policies, lease ownership, or rate limits are evaluated THEN the system SHALL CONTINUE TO enforce them and SHALL not bypass or weaken them merely to obtain a passing test result.

3.4 WHEN a run reaches its configured target or an approved stop condition THEN the system SHALL CONTINUE TO avoid unnecessary discovery, enrichment, provider, queue, assignment, and delivery work while preserving valid completed effects and reconciling counts.

3.5 WHEN enrichment, provider, queue, assignment, or delivery work partially fails THEN the system SHALL CONTINUE TO preserve valid partial results, classify retryable and non-retryable failures, and expose an actionable shortfall without fabricating completion.

3.6 WHEN local Docker Compose, isolated, staging, or live evidence is collected THEN the system SHALL CONTINUE TO label the evidence by environment and verification class, keep secrets out of logs and artifacts, retain synthetic unit fixtures for unit/contract tests, and avoid treating synthetic runtime or local results as proof of the configured real Supabase/provider path, live provider, deliverability, or production readiness.

3.7 WHEN a safe substitute, sandbox, or synthetic unit fixture is used to validate a previously blocked path THEN the system SHALL CONTINUE TO keep the substitute isolated from working client data and SHALL preserve all authentication, RLS, tenant, quota, rate-limit, provider, and outbound-side-effect protections. Synthetic unit fixtures SHALL not be promoted to synthetic runtime readiness evidence.

3.8 WHEN the follow-up validation profile is started, exercised, or cleaned up THEN the system SHALL CONTINUE TO leave production and shared services, production data, real recipients, `.env` secrets, provider credentials, tenant controls, quotas, rate limits, provider guards, outbound protections, audit controls, and stop controls unchanged. A failed prerequisite, rollback, or cleanup boundary SHALL remain an explicit `BLOCKED`, `FAIL`, or `NOT TESTED` result rather than being hidden or repaired through a bypass.
