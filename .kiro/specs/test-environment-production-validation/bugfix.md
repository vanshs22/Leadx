# Bugfix Requirements Document

## Introduction

LeadX needs a safe, bounded end-to-end validation profile for the current project. The requested broad authentication and permission bypass is not acceptable for production, staging, or any approved real tenant. The validation profile must use only disposable local/test boundaries, preserve tenant checks and production guards, avoid all secret handling, and report unavailable prerequisites as `BLOCKED` rather than weakening controls or inferring success.

This specification covers test-only fixtures, deterministic replay checks, authenticated browser checks using ephemeral state, one bounded real target-five validation after local gates pass, and cleanup/guard restoration. It does not authorize application-code changes, production migrations, destructive resets, email, outreach, campaigns, Stripe, SES, or credential handling.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN end-to-end validation requires authentication or tenant-scoped data THEN the current local evidence can stop at offline contracts because no disposable authenticated fixture and explicitly tagged synthetic tenant/ICP are available.

1.2 WHEN durable first, same-key, conflicting, or fresh replay behavior is evaluated THEN the current validation boundary does not provide one deterministic local/test replay fixture that proves no duplicate work and no cross-tenant access.

1.3 WHEN authenticated client/admin Playwright checks are attempted THEN the current validation can report browser checks as unavailable without a standard ephemeral auth/storage-state setup, target-five task trace, count, and realtime matrix.

1.4 WHEN a real target-five validation is considered THEN local/test readiness, forbidden-action guards, timing limits, count reconciliation, and cleanup/guard restoration are not one explicit prerequisite gate.

1.5 WHEN a test-only permission shortcut is proposed THEN it could disable authentication, tenant checks, RLS, or production guards and make dummy data appear valid without proving the real security boundary.

### Expected Behavior (Correct)

2.1 WHEN local/test end-to-end validation is prepared THEN the system SHALL use an explicitly tagged disposable test tenant and synthetic ICP through an approved test-only mechanism, preserve tenant checks, isolate providers locally, bound all records for cleanup, and never use the approved real tenant.

2.2 WHEN replay validation runs against the local/test boundary THEN the system SHALL use a deterministic durable fixture to prove first submission, same-key replay, conflicting replay rejection, and fresh-key admission without duplicate active work, cross-tenant disclosure, or uniqueness/RLS bypass.

2.3 WHEN authenticated browser validation runs THEN the system SHALL use ephemeral authentication and storage state created outside chat or generated by an approved fixture, avoid printing or persisting credentials, and cover client/admin target-five flow, task trace, counts, realtime reconciliation, loading, error, and empty states.

2.4 WHEN a bounded real target-five run is considered THEN it SHALL be allowed only after local/test exploration, preservation, fixture, replay, browser, and guard-parity gates pass; it SHALL use a fresh scoped identity, a hard cap of 500, no email/outreach/campaign/Stripe/SES action, and explicit `BLOCKED` reporting when prerequisites are absent.

2.5 WHEN the bounded real target-five run completes THEN the validation SHALL verify assigned >=5, delivered >=5, truthful `completed` status, CRM/client count reconciliation, task trace and realtime convergence, measured timing, zero forbidden actions, bounded cleanup, and restoration of production guards.

2.6 WHEN any validation step cannot be safely observed or a guard-parity check fails THEN the validation SHALL stop and record `BLOCKED`, `FAIL`, or `NOT_TESTED`; it SHALL not disable authentication/RLS/tenant checks, perform a destructive reset, or claim production readiness.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN validation runs outside the disposable local/test profile THEN the system SHALL CONTINUE TO require normal authentication, tenant authorization, RLS, provider policy, and production/staging guards.

3.2 WHEN the approved real tenant or production/staging boundary is encountered THEN the system SHALL CONTINUE TO reject test-fixture provisioning and test-only permission changes.

3.3 WHEN local provider-isolated tests run THEN the system SHALL CONTINUE TO deny unapproved provider calls and preserve email, outreach, campaign, Stripe, and SES exclusion.

3.4 WHEN durable jobs, idempotency keys, assignments, CRM rows, or realtime invalidations are tested THEN the system SHALL CONTINUE TO preserve uniqueness, tenant scope, authoritative state, and metadata-only invalidation/refetch behavior.

3.5 WHEN validation completes or is blocked THEN the system SHALL CONTINUE TO restore production guard configuration and remove or retain only explicitly bounded, tagged evidence required by the runbook; it SHALL not reset unrelated data.
